# pm — 複数案件の Claude Code セッションを tmux で管理する

WSL 2 上で、案件ごとの Claude Code セッション（子）と、案件の中身を知らない窓口セッション（親）を 1 つの tmux セッションに並べて動かすツールです。

```text
┌ 親AI ───────────────┬ 課題一覧 ───────────┐
│ claude --name parent│ watch -n 5 pm status│
├ 子：案件A ──────────┼ 子：案件B ──────────┤
│ claude --name A     │ claude --name B     │
└─────────────────────┴─────────────────────┘
```

## 構成の要点

- 親は別の Linux ユーザー（既定 `pm-parent`）で動かします。案件ディレクトリは Unix の権限で親から読めません。これが「機密情報の分離」の実体です。`--single-user` で同一ユーザー構成も選べますが、その場合は誤操作防止の水準になります。
- 親と子の連絡は Claude Code のセッション間メッセージを使わず、ファイル経由です。親が `inbox/<案件>.md` に追記し、`pm dispatch`（tmux 内の監視処理）が追記分を子ペインへ入力します。子からの報告は課題ファイル `status/<案件>.md` の更新です。
- 子は案件ディレクトリで通常どおり `claude` を起動します。ルールは `--append-system-prompt-file` で渡し、案件内の `CLAUDE.md` は触りません。
- 利用者の `~/.tmux.conf` は変更しません。マウス操作などはセッション `pm` に限定して設定します。

## ディレクトリ

| パス | 内容 |
|---|---|
| `~/pm/` | 親の起動場所。別ユーザー構成では `/srv/pm` への symlink（親ユーザーの `~/pm` も同じ先） |
| `~/pm/CLAUDE.md` | 親のルール |
| `~/pm/.claude/settings.json` | 親の権限設定 |
| `~/pm/.claude/skills/` | `/add-task`、`/show-task` |
| `~/pm/status/<案件>.md` | 課題ファイル。子が書き、親と課題一覧が読む |
| `~/pm/inbox/<案件>.md` | 親が書く依頼の記録。監視処理が読む |
| `~/pm/workspaces.txt` | 案件名の一覧（パスを含まない）。親はこれで案件名を知る |
| `~/.config/pm/workspaces` | 案件名とパスの対応表（TSV）。親からは読めない |
| `~/.config/pm/handoff/<案件>.md` | 引き継ぎメモ。その子だけが読み書きする |
| `~/.config/pm/generated/<案件>/` | 子ごとに生成する設定とルール |
| `~/.config/pm/state/` | ペイン対応表、inbox の送信済み位置 |
| `~/.config/pm/config` | `install.sh` が書く設定（共有ディレクトリ、親ユーザー名） |

## 前提

- Windows 上の WSL 2（Ubuntu など）、bash、tmux 3.2 以上、Claude Code 2.1.224 以上
- 親のサンドボックスに `bubblewrap` と `socat`：`sudo apt-get install bubblewrap socat`。別ユーザー構成では `/usr/bin/bwrap` が要ります。linuxbrew で入れた `bwrap` はあなたの PATH にしかなく、親ユーザーからは使えません
- 別ユーザー構成では sudo が使えること

## 導入

```bash
git clone https://github.com/Atsu-Imo/pm.git ~/workspace/pm
cd ~/workspace/pm
./install.sh            # 別ユーザー構成（既定）
# ./install.sh --single-user   # 同一ユーザー構成
```

`install.sh` が行うこと（別ユーザー構成）：

1. `~/.local/bin` に `pm`、`pm-child`、`pm-hook`、`pm-lib.sh` を置く。既存ファイルと内容が違えば `*.bak.<日時>` に退避する
2. `~/.config/pm/` を作る（対応表は空）
3. sudo で、グループ `pm` とユーザー `pm-parent` を作り、`/srv/pm` を用意し、root 所有の起動ラッパ `/usr/local/bin/pm-parent-run` を置く。`/etc/sudoers.d/pm` には「あなたが `pm-parent` としてこのラッパだけをパスワードなしで実行できる」規則を置く。ラッパが受け付ける引数は `--resume` と `--check` のみ
4. `~/pm` と `/home/pm-parent/pm` を `/srv/pm` への symlink にする
5. あなたのホームが他ユーザーから読める権限なら `chmod 750` を提案する
6. `pm-parent` に `claude` が無ければ公式インストーラの実行を提案する（ネットワークを使う）
7. 親の `CLAUDE.md`、`settings.json`、スキルを `/srv/pm` に置く

繰り返し実行しても壊れません。何かを置き換える前に退避します。`--shared` にホームや中身のある既存ディレクトリを渡すと停止します。pm が管理するディレクトリには目印 `.pm-managed` を置き、`uninstall.sh --purge` はこれがある場所しか消しません。`--yes` を付けても、ホームの権限変更と `pm-parent` への claude のネットワークインストールは個別に確認します。

導入後の手順：

```bash
# グループ追加を反映する。ログインし直す（newgrp pm はそのシェルにしか効かない）。
# 既に tmux サーバが動いていれば tmux kill-server で止めてから入り直す
# （tmux の中で動く監視処理が古いグループのままだと inbox を読めない）

# 親ユーザーで一度ログインする（ブラウザで承認。初期設定が終わったら /exit）
sudo -H -u pm-parent bash -lc 'cd ~/pm && claude'

# 案件を登録する（パスに空白があっても可）
pm add-workspace case-a ~/workspace/case-a
pm add-workspace case-b "/path/with space/case-b"

# 前提を点検して起動する
pm check
pm init
```

親ユーザーのログインが別途必要なのは、Claude Code の認証情報が Linux ユーザーごとのホームに保存されるためです。同じ Anthropic アカウントで構いません。`claude` 本体も親ユーザーのホームに別途入ります（あなたの `~/.local/bin/claude` は親ユーザーから読めないため）。

## 日常の使い方

起動と接続：

- `pm init` で起動します。tmux セッション `pm` が既にあれば接続するだけです
- 画面を閉じるときは tmux からデタッチします。`Ctrl-b` を押して離し、次に小文字の `d` を押します。同時押し、`Shift` 付きの `D`（クライアント選択画面が開く）、日本語入力オンでは効きません
- キーで駄目なら `Ctrl-b` → `:` のあと `detach` と打って Enter、または別のターミナルから `tmux detach-client -s pm`
- 戻るときは `pm init`（`tmux attach -t pm` と同じ）。セッションは残っているので会話はそのまま続きます
- 完全に止めるときは `tmux kill-session -t pm`。次の `pm init --resume` で親子とも前の会話を再開できます。課題ファイルと引き継ぎメモは tmux を止めても残ります

タスクの流れ：

- 親ペインで `/add-task <案件名> <内容>` と打ちます。案件名は登録時の英数字名、内容は日本語で構いません。例：`/add-task case-a 経費精算の CSV 出力を 11/10 までに直す`
- 数秒後に子ペインへ「【親からの依頼】…」として入力され、子が課題ファイルに `#番号` を振って追加します。課題一覧ペインに出れば受領済みです
- 追記や変更は番号で指します。`/add-task case-a #3 の対象は api 配下だけ`。子は行を増やさず該当タスクを書き換えます。番号を付けず内容で指しても、子が既存タスクに当てはめます
- 子ペインで直接話しかけても構いません。親経由は「複数案件をまとめて窓口から出したい」ときの手段で、子に直接頼んだ内容も子が課題ファイルに書けば一覧に出ます
- 子ペインで行った作業は自動では親に伝わりません。親が知るのは課題ファイルの内容だけです
- 確認が要る操作（コミット、削除、外部送信など）は子が子ペインで聞いてきます。親からの依頼は承認扱いになりません

このリポジトリを更新したあと：

- `./install.sh` を再実行します。変更が無い部分は sudo を使いません
- 子のルール（`share/child/rules.md`）や子の設定を変えたら、`pm restart <案件名>` で子を起動し直すと反映されます
- 親のルールや設定、スキルを変えたら、`tmux kill-session -t pm` のあと `pm init --resume` で起動し直します（`pm restart` は子専用です）

## コマンド

通常のシェルで実行するもの：

| コマンド | 動作 |
|---|---|
| `pm init` | tmux セッション `pm` を作り、親、課題一覧、登録済みの全案件、inbox 監視を起動して接続する。既にあれば重複起動せず接続する。足りないペインがあれば補う |
| `pm init --resume` | 新規作成時に、親子とも以前の会話を名前で再開する（`claude --resume <名前>`）。セッションが起動中なら無視して接続する |
| `pm add-workspace <名前> <パス> [--model <モデル>]` | 案件を登録し、課題ファイルと引き継ぎメモを作る。起動中ならペインを追加する。`--model` でその子のモデルを指定できる |
| `pm set-model <名前> <モデル\|default>` | その案件の子が使うモデルを変える。`default` で指定を外す。次の起動（`pm restart`）から有効 |
| `pm status [--brief\|--all]` | 全案件の状態、未完了件数、モデルと、未完了タスクの期限・直近の作業を、パスを出さずに表示する。`--brief` で件数だけ、`--all` で完了済みも |
| `pm restart <名前>` | その子に引き継ぎメモの更新を依頼し、更新を待ってから（最大 180 秒）、そのペインだけを新しいセッションで起動し直す。子が権限確認などの選択待ちに見えるときは何もせず停止する |
| `pm list` | 登録済みの案件名 |
| `pm check` | 前提条件の点検 |

案件名に使えるのは英数字、ハイフン、アンダースコアだけです（先頭は英数字）。`parent`、`status`、`main`、`sys` は予約語です。パスにタブ、改行、二重引用符、バックスラッシュを含むものは登録できません（対応表と生成する JSON を壊すため）。

親セッションで実行するもの：

| コマンド | 動作 |
|---|---|
| `/add-task <案件> <内容>` | `inbox/<案件>.md` に 1 行追記する。数秒後に子ペインへ「【親からの依頼】…」として入力される |
| `/show-task <案件>` | `status/<案件>.md` を表示する |

どちらも `disable-model-invocation: true` で、利用者が打ったときだけ動きます。

## モデル

- 親は `~/pm/.claude/settings.json` の `"model": "opus"`（Claude Opus 5.5）で固定しています。変えるにはこのファイルを編集するか、親ペインで `/model` を打ちます（親ユーザーの設定として保存されます）。
- 子は案件ごとに決められます。`pm add-workspace ... --model opus` または `pm set-model <名前> sonnet` で対応表に記録し、`pm-child` が `--model` で渡します。指定が無い案件はあなたの Claude Code の既定モデルです。
- 子ペインで `/model` を打つと、Claude Code はそれをあなたの既定として保存します。案件ごとの指定には `pm set-model` を使ってください。

## 画面

- 1 枚目のウィンドウ `main` に親、課題一覧、子 4 件まで。5 件目からは `ws-2`、`ws-3`… に 5 件ずつ入ります（`PM_FIRST_WINDOW_CHILDREN`、`PM_CHILDREN_PER_WINDOW` で変更可。`~/.config/pm/config` に書く）
- 各ウィンドウは `tiled` レイアウトです。子 2 件のときに図のとおり 2×2 になります
- ペインの枠にタイトル（親AI、課題一覧、子：案件名）を表示します
- `sys` ウィンドウに inbox 監視が動いています。通常は見る必要がありません
- 子が終了してもペインは残ります（`remain-on-exit`）。`pm init` を再実行すると起動し直します

## 子セッションの動き

- 起動時に `SessionStart` フックが課題ファイルと引き継ぎメモを読み込ませます。子は状況を短く報告して指示を待ちます。読み込んだだけでは作業を始めません
- タスクの受領時・完了時・重要な判断時・中断時に課題ファイルと引き継ぎメモを更新します
- 引き継ぎメモが 30 分以上更新されていないと、`Stop` フックが応答の終わりに更新を促します（`PM_HANDOFF_STALE_MIN` で変更可）
- 手動 `/compact` の際にメモが 5 分以上古ければ一度だけ止めて更新を促します。自動圧縮は止めません。圧縮後の最初のプロンプトでメモの確認を促します
- 親からの依頼は利用者の承認として扱いません。確認が要る操作は子ペインで利用者に直接聞きます。権限確認の待ちには利用者がそのペインで答えます

課題ファイルの形式（タスク1件につき3行。番号は子が受領時に振る）：

```markdown
# 案件名
更新：YYYY-MM-DD HH:MM
状態：作業中 / 入力待ち / 完了

- [ ] #3 ログ出力を整理する
  期限：2026-11-10
  直近：11-04 15:20 api/ 配下の出力箇所を洗い出した
- [x] #2 テストを追加する
  期限：なし
  直近：11-04 14:50 完了
```

- 期限は依頼文に「11/10まで」のように書けば子が `YYYY-MM-DD` に直して記録します。無ければ「なし」。
- 「直近」は子がそのタスクに触れるたびに上書きする、時刻と一行要約です。
- 既存タスクへの補足は `#3 の対象は api 配下だけ` のように番号で指します。子は行を増やさず該当タスクを書き換えます。
- 課題一覧ペインは常時展開で、期限を過ぎたタスクには `!` が付きます。

## 隠蔽の範囲と残る経路

別ユーザー構成で親から読めないもの：案件ディレクトリ（ホームが 750 の場合）、`~/.config/pm`、あなたの `~/.claude`（履歴、セッション一覧、プロジェクト記録）、`/proc/<pid>/cwd` と環境変数（同じ UID 限定）、tmux のソケット（`/tmp/tmux-<uid>` は 700）。

残る経路：

- 案件が `/mnt/c` など Windows 側のマウント配下にあると、WSL の既定では全ユーザーから読めます。`pm check` が警告します。対策は `/etc/wsl.conf` の automount オプションで権限を絞るか、案件を Linux 側に置くことです
- `/proc/<pid>/cmdline` は全ユーザーから読めます。子は `pm-child <名前>` 経由で起動し、cd してから `claude` を exec するので、コマンドラインにパスは載りません。ただし子の中で起動したサブプロセスが引数にパスを取ると載ります
- `/srv/pm/status` と `inbox` の内容は親が読めます。子はそこに絶対パスを書かないルールですが、モデルへの指示であり強制ではありません
- 親の Bash は `tmux`、`pm`、`sudo`、`claude` を文字列一致で拒否しています。公式ドキュメントどおり、これは境界ではなく誤操作防止です。別ユーザー構成では、仮に通っても tmux ソケットと対応表に権限がありません
- 子はあなたのユーザーで動くので、同じ tmux サーバと sudoers の規則に届きます。子の設定で `sudo` と `tmux` を拒否していますが、これも文字列一致です。sudoers の規則を起動ラッパ 1 本に限定しているのは、仮に通っても親の認証情報や会話ログに届かないようにするためです

同一ユーザー構成（`--single-user`）では、上のすべてが設定による拒否だけになります。`Read` ツールの拒否と Bash のサンドボックス `denyRead` で案件パスを塞ぎますが、`Read` 以外のツールや MCP、WebFetch はサンドボックス外です。機密分離には足りません。

## 困ったとき

- `pm init` が `no such session: =pm` などで止まる：作成途中で失敗したセッションが残っています。`tmux kill-session -t pm` のあと再実行してください
- 親ペインがすぐ終了する：`pm check` を実行してください。別ユーザー構成で多いのは `/usr/bin/bwrap` が無い（linuxbrew 版しか無い）ケースで、`sudo apt-get install bubblewrap` で直ります
- `/add-task` したのに課題一覧が更新されない：まず `sys` ウィンドウの監視処理にエラーが出ていないか見ます。`inbox` を読めていない場合、導入直後にログインし直さず起動した tmux サーバがグループ `pm` を持っていないのが原因です。`tmux kill-server` のあとログインし直して `pm init --resume` するか、応急処置として `sudo chmod 2775 /srv/pm/inbox` を実行します
- 子が「権限確認の選択待ち」で止まっている：そのペインで利用者が答えます。監視処理は選択待ちに見えるペインには入力を送りません
- `pn init` と打つと pnpm が動いて `package.json` が作られます。`pm init` です

## 削除

```bash
./uninstall.sh          # コマンドと sudoers 規則を消す。課題ファイルと引き継ぎメモは残す
./uninstall.sh --purge  # 設定、共有ディレクトリ、親ユーザーも消す（確認あり）
```

## テスト

```bash
bash tests/run.sh
```

tmux と claude を `tests/stubs/` の代役に差し替えて動かします。実際のプロセスは起動しません。実機での確認項目は `docs/CHECKLIST.md` にあります。

## 設定値

`~/.config/pm/config` に書けるもの（すべて環境変数でも上書き可）：

| 変数 | 既定 | 内容 |
|---|---|---|
| `PM_SHARED` | `/srv/pm` | 親の起動場所の実体 |
| `PM_PARENT_USER` | `pm-parent` | 親のユーザー。空なら同一ユーザー |
| `PM_FIRST_WINDOW_CHILDREN` | 4 | 1 枚目のウィンドウの子の数 |
| `PM_CHILDREN_PER_WINDOW` | 5 | 2 枚目以降の子の数 |
| `PM_STATUS_INTERVAL` | 5 | 課題一覧の更新間隔（秒） |
| `PM_DISPATCH_INTERVAL` | 2 | inbox 監視の間隔（秒） |
| `PM_RESTART_WAIT` | 180 | `pm restart` でメモ更新を待つ上限（秒） |
| `PM_HANDOFF_STALE_MIN` | 30 | メモが古いと見なす分数 |
